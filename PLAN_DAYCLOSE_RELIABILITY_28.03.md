# План повышения надёжности day close

**Цель:** повысить надёжность потока закрытия дня (Telegraf, Vercel) без переписывания всего бота: секрет webhook, персистентность состояния, обработка ошибок доставки апдейтов, календарь по часовому поясу пользователя, проверка владельца при обновлении задач.

---

## Состав плана

1. **WEBHOOK_SECRET в production** — обязательная проверка секретного токена для POST webhook в проде.
2. **Снижение зависимости day close от in-memory session** — критичные шаги не должны ломаться из‑за cold start / разных инстансов на Vercel.
3. **Pending в БД** — ожидание текстовых ответов (и при необходимости смежных шагов) хранить в персистентном слое (например `users.meta`), а не только в сессии Telegraf.
4. **Ошибки webhook** — не терять апдейты молча; осмысленная реакция на сбой обработки (с учётом ретраев Telegram).
5. **Timezone** — календарные «сегодня / завтра» и согласованные вычисления для day close и зависимых сервисов по `users.timezone`.
6. **updatePlanItem + userId** — обновление `plan_items` только при совпадении `user_id`, плюс базовая обработка ошибок после update.

---

## Рекомендуемый порядок внедрения

1. П.6 — updatePlanItem + userId  
2. П.5 — timezone  
3. П.3 — Pending в БД  
4. П.4 — ошибки webhook  
5. П.1 — WEBHOOK_SECRET в production  
6. П.2 — снижение зависимости от session

## Правила работы по плану

- Работаем **по одному пункту** за раз.
- **Не расширяем scope** сверх согласованного для пункта.
- **Не делаем рефакторинг «заодно»** — только то, что нужно для пункта.
- **Перед коммитом** — аудит границ изменений (какие файлы, нет ли лишнего).
- **После завершения пункта** — обновить статус в этом файле.

---

## Что не входит автоматически

- Смежные улучшения **вне** активного пункта плана.
- **Деплой** (отдельное решение / процесс).
- **Архитектурные переделки** без отдельного решения.
